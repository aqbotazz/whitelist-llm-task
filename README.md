# Извлечение данных из документов (тестовое задание LLM Engineer)

CLI получает текст документа (счёт, коммерческое предложение, акт) и возвращает JSON
по фиксированной схеме. Главная цель — **не выдумывать**: чего нет в документе, то `null`.

## Запуск с нуля

Нужны Python 3.10+ (проверено на 3.12, macOS) и `make`. **Ключ API для тестов и eval не нужен**:
eval воспроизводит записанные ответы модели (см. раздел «Модель»).

```bash
git clone <ссылка на репозиторий>
cd whitelist-llm-task
make install      # создаёт .venv и ставит зависимости из requirements.txt
make test         # 25 тестов pytest
make eval         # прогон 11 документов, метрики по полям
.venv/bin/python -m extractor.cli data/docs/03_invoice_kokzhiek_ocr.txt   # один документ → JSON
```

Без `make` — те же команды вручную:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pytest -v
.venv/bin/python eval.py
```

Переменные окружения (нужны **только** для `--live`, задаются в `.env`, образец — `.env.example`):

| Переменная | Что это |
|---|---|
| `GEMINI_API_KEY` | бесплатный ключ Google AI Studio: https://aistudio.google.com/apikey |
| `GEMINI_MODEL` | имя модели, по умолчанию `gemini-3.5-flash-lite` |

## Структура

```
extractor/schema.py    # схема выхода (pydantic): типы, форматы, допустимые значения
extractor/pipeline.py  # промпт, вызов модели, валидация с повтором, деградация
extractor/checks.py    # проверки кодом: цитата в тексте, OCR, БИН, прописью, даты, арифметика
extractor/llm.py       # вызов Gemini, запись/воспроизведение ответов
extractor/cli.py       # командная строка
eval.py                # мини-eval
data/docs/             # 11 тестовых документов
data/expected/         # эталонные JSON
data/llm_cache/        # записанные ответы модели (промпт + сырой ответ)
tests/                 # тесты pytest
```

## Как это работает

```
текст → промпт → модель → JSON со значениями и цитатами
      → валидация pydantic (не прошла → повтор с текстом ошибки, до 2 раз → невалидные поля в null)
      → проверка по тексту: цитата есть в документе и значение из неё следует (иначе null + warning)
      → детерминированные проверки: контрольная сумма БИН, несколько сумм «к оплате», арифметика
      → field_confidence считает код
```

Главный механизм против выдумок — **цитата-доказательство**. Модель обязана к каждому значению
приложить точную цитату из текста. Код проверяет, что цитата реально есть в документе и что
значение из неё следует (число написано в цитате цифрами или прописью, дата в цитате та же,
БИН — те же 12 цифр). Не подтвердилось → `null` + warning.

`field_confidence` считает код, а не модель: 1.0 — значение найдено в тексте как есть;
0.9 — сумма взята из записи прописью; 0.7 — значение восстановлено после исправления OCR
или выбрано из нескольких противоречащих; 0.6 — не сошлась арифметика; 0.5 — БИН не проходит
контрольную сумму. Указывается только для заполненных полей.

### Что происходит, если ответ не прошёл валидацию

1. Ответ модели — не JSON или не проходит схему (неверный тип документа, БИН не из 12 цифр,
   дата не в формате YYYY-MM-DD, число строкой «186 180 тг»…) → модели отправляется тот же промпт
   плюс текст ошибки pydantic, и она отвечает заново. Максимум 2 повтора.
2. Не помогло, но JSON есть → только невалидные поля становятся `null` (тип → `unknown`,
   сломанная позиция удаляется), в `warnings` — какое поле и почему. Остальные данные сохраняются.
3. Не помогло и JSON нет совсем → `doc_type: unknown`, все поля `null`, warning с ошибкой.

Реальный случай из первого прогона: модель вернула позиции в виде
`"qty": {"value": 50, "quote": "50"}` вместо числа. Pydantic отклонил ответ, повтор с текстом
ошибки дал правильный формат. После этого в промпт добавлен пример позиции. Поведение покрыто
тестами с фейковой моделью (см. `tests/`).

## Модель

**Gemini (`gemini-3.5-flash-lite`) через бесплатный ключ Google AI Studio**, пакет `google-genai`,
`temperature=0`, режим ответа JSON.

- Платный API не нужен, а бесплатного лимита хватает на набор из 11 документов.
- Задача — извлечение по строгим правилам, а не рассуждение, поэтому лёгкой модели хватает.
  Защиту от ошибок модели обеспечивает код, а не размер модели. Это ещё и самый дешёвый вариант,
  что важно для бюджета ~0,5 ₸ на документ (см. REFLECTION.md).
- Изначально я планировала `gemini-2.5-flash`, но она закрыта для новых ключей. Более новые Flash
  (`gemini-3.5/3.7/3.8-flash`) в момент работы отвечали `503 high demand`. Модель меняется
  одной строкой `GEMINI_MODEL` в `.env`.

### Записанные ответы модели (replay) и живой режим (live)

Чтобы проверяющие могли всё запустить **без ключа**, настоящие ответы модели сохранены в
`data/llm_cache/` (в каждом файле — модель, полный промпт и сырой ответ). Файл ищется по хешу
промпта.

- **По умолчанию (replay)** — ответ модели берётся из файла. Всё остальное (валидация, повторы,
  проверки по тексту, метрики) работает по-настоящему.
- **`--live`** — вызывается настоящая модель, ответ перезаписывается. Нужен ключ:

```bash
cp .env.example .env      # и вписать ключ в GEMINI_API_KEY
.venv/bin/python -m extractor.cli data/docs/01_invoice_almaty_trade.txt --live
```

Если изменить промпт или документ, записанного ответа не будет, и программа попросит запустить `--live`.

## Тестовый набор

11 документов в `data/docs/`, к каждому эталон в `data/expected/` с тем же именем.
01–03 — от заказчика, 04–11 — свои.

| № | Что проверяет |
|---|---|
| 01 | Счёт заказчика; БИН с неверной контрольной суммой; что считать «итого» |
| 02 | КП: нет БИН/номера/НДС/итога, две даты (срок действия и составление), qty не указано |
| 03 | Казахско-русский текст, OCR-ошибки в БИН, «қазан» = октябрь, сумма прописью, «НДС не облагается» |
| 04 | Акт в USD, исполнитель и заказчик с разными БИН |
| 05 | Счёт, где БИН покупателя стоит раньше БИН поставщика |
| 06 | **Сложный:** сумма только прописью по-русски, ИП с ИИН, нет количества и цены |
| 07 | **Сложный:** две разные суммы «к оплате» и две даты документа |
| 08 | **Сложный:** OCR-шум в суммах и дате, нечитаемая сумма НДС (нельзя досчитать) |
| 09 | **Сложный:** полностью на казахском, НДС записан как ҚҚС |
| 10 | Ставка «НДС 16%» без суммы — НДС не считаем; двуязычное название; EUR |
| 11 | **Сложный:** письмо-приглашение, не счёт/КП/акт → `unknown`; внутри есть сумма и даты-ловушки |

Поле `warnings` в эталоне — это описание предупреждений, которые система обязана выдать,
а не точный текст. `field_confidence` в эталоне пустой: его считает код, с эталоном его не сравниваем.

## Решения по неоднозначностям

1. **`total_amount`** — итоговая сумма **к оплате** (с НДС, если он есть), а не «итого» без НДС.
2. **«НДС не облагается» / «Без НДС»** → `vat_amount = 0`: документ прямо говорит, что НДС нет.
   Это факт из текста, а не расчёт. Если про НДС ничего не сказано или указана только ставка
   («НДС 16%» без суммы) → `null`. Сами НДС не вычисляем.
3. **Две суммы «итого»** — берём ту, что сходится с суммой строк (+ НДС); если не сходится ни одна —
   последнюю сумму «к оплате». В обоих случаях — warning.
4. **Две даты** — противоречием считаем только случаи, когда обе даты претендуют на роль даты документа.
   Срок действия КП, срок оплаты, дата мероприятия — это другие роли, не противоречие.
   Если противоречие есть — берём дату из заголовка (рядом с номером документа) + warning.
5. **OCR-ошибки** — исправляем только путаницу «буква вместо цифры» в числовых полях
   (O/о→0, l/I/i→1, в БИН, датах и суммах) и только если результат однозначен.
   После исправления — warning и пониженный confidence. Нечитаемое (`1O #8~`) → `null` + warning.
6. **Двуязычное название** — берём русский вариант с правовой формой (`ТОО "Кокжиек Курылыс"`).
   Если название есть только на казахском — берём как написано, не переводим.
7. **БИН** — только поставщика (исполнителя), БИН покупателя игнорируем. У ИП вместо БИН — ИИН,
   записываем его в `supplier_bin`. БИН с неверной контрольной суммой **не обнуляем** (он есть
   в документе), но снижаем confidence и пишем warning.
8. **`qty` / `price`** — не указаны → `null`, а не 1. `price` — цена за единицу.
9. **Тип документа** — по заголовку: «шот-фактура» (каз.) = счёт-фактура → `invoice`.
   Если номер/текст намекает на другой тип (`AKT-09` у шот-фактуры) — warning.
10. **`unknown`** — для документа не из списка (письмо, приглашение) все поля `null`:
    отправитель письма — не «поставщик», а сумма в тексте — не сумма документа.

## Тесты

```bash
make test
```

25 проверок, без сети и без ключа. В тестах пайплайна вместо модели — **фейковая модель**,
которая нарочно выдумывает и ломает ответ:

| Файл | Что проверяет |
|---|---|
| `tests/test_checks.py` | контрольная сумма БИН; исправление OCR только в «числовых» словах; сумма прописью (рус. и каз.); даты во всех форматах; схема отклоняет 7 видов неверных данных |
| `tests/test_pipeline.py` | выдуманный БИН с несуществующей цитатой → `null`; настоящая цитата, но значение из неё не следует (сложила строки КП, сегодняшняя дата, qty = 1) → `null`; НДС, посчитанный из ставки → `null`; БИН покупателя → `null`; не JSON → повтор с текстом ошибки → успех с 3-й попытки; повторы кончились → обнуляется только сломанное поле; совсем нет JSON → `unknown`; две суммы «к оплате» → берётся сходящаяся со строками; БИН с плохой контрольной суммой сохраняется с confidence 0.5; не сходится арифметика → warning; БИН с OCR-ошибками восстановлен |
| `tests/test_eval.py` | галлюцинация, пропуск и неверное значение считаются раздельно; qty = 1 вместо `null` — галлюцинация; лишняя и недостающая позиции |

Проверка, что тесты не «пустые»: если отключить проверку по тексту (цитата и значение),
падают 4 теста на выдумки.

## Eval

```bash
make eval                           # записанные ответы модели, ключ не нужен
.venv/bin/python eval.py --live     # вызвать модель заново (нужен ключ)
```

Для каждого поля каждого документа исход — один из четырёх:
**верно** (совпало или оба `null`), **галлюцинация** (заполнено, а в эталоне `null`),
**пропуск** (`null`, а в эталоне есть значение), **неверно** (оба не `null`, но разные).
Строки сравниваются без учёта регистра, кавычек и точки в конце, числа — до копейки.
Позиции сравниваются по порядку: `qty` и `price` — отдельно (ловушка «qty = 1, когда количества нет»),
название — мягко (одно содержится в другом), лишняя позиция — галлюцинация, недостающая — пропуск.
Дополнительно: выдала ли система предупреждение там, где эталон его ожидает.

Результат на `gemini-3.5-flash-lite` (replay записанных ответов):

```
поле               точность  верно  галлюц.  пропуск  неверно
-------------------------------------------------------------
doc_type               100%     11        0        0        0
supplier_name           91%     10        0        0        1
supplier_bin           100%     11        0        0        0
doc_number             100%     11        0        0        0
doc_date               100%     11        0        0        0
currency               100%     11        0        0        0
total_amount           100%     11        0        0        0
vat_amount             100%     11        0        0        0
line_items.qty         100%     18        0        0        0
line_items.price       100%     18        0        0        0
line_items.name        100%     18        0        0        0
-------------------------------------------------------------
ИТОГО                   99%    141        0        0        1

Предупреждения выданы в 5 из 5 документов, где они ожидались
```

Единственная ошибка: в документе 09 модель вернула `Алтын Дала` без правовой формы `ЖШС`.

**Честная оговорка.** Сырые ответы модели (до проверок кода) на этом наборе тоже почти
безошибочны: проверки не изменили ни одного значения. Но и ни одного правильного значения
не испортили — ложных срабатываний нет. То есть набор из 11 документов не нагружает защиту
от галлюцинаций на настоящей модели. Что защита действительно ловит выдумки, показано тестами
с фейковой моделью (`tests/`). Вклад кода, который виден на реальном прогоне: предупреждения
о контрольной сумме БИН, OCR, сумме прописью и «номер похож на акт». В документе 09 модель
сама ошиблась в арифметике (написала, что 480 000 + 76 800 ≠ 556 800), а проверка кода
этой ошибки не повторила. 11 документов — слишком мало для выводов о точности модели.

## Что сделано и что нет

**Сделано**

- CLI: текст документа → JSON по схеме из задания.
- Валидация pydantic, повтор с текстом ошибки (до 2 раз), деградация только сломанных полей.
- Защита от выдумок: цитата-доказательство к каждому полю и проверка кодом, что цитата
  есть в тексте и значение из неё следует.
- Проверки кодом: контрольная сумма БИН/ИИН, исправление OCR (O→0, l/I→1), сумма прописью
  (русский и казахский), даты (цифрами, по-русски, по-казахски), несколько сумм «к оплате»,
  арифметика строк + НДС = итог, БИН покупателя вместо поставщика, «номер похож на акт».
- `field_confidence` считает код.
- 11 документов с эталонами, eval с раздельным подсчётом галлюцинаций / пропусков / неверных значений.
- 25 тестов, в том числе с фейковой моделью.
- Запись настоящих ответов модели, чтобы всё запускалось без ключа.

**Не сделано / ограничения**

- **Две даты документа** находит только модель (в `warnings`). Кодом это не проверяется:
  чтобы отличить «дату документа» от «срока оплаты», нужно понимать роль даты в тексте.
  Код только проверяет, что выбранная дата действительно написана в цитате.
- **Исправление OCR** — только путаница букв и цифр (O/l/I) в «числовых» словах. Другие ошибки
  (3↔8, 5↔S, разорванные числа) не исправляются: поле получит `null`.
- **Парсер суммы прописью** простой: целые суммы до миллионов, без копеек прописью и без
  редких форм («полторы тысячи»).
- **Проверка названия поставщика** — только «значение содержится в цитате». Модель может
  обрезать правовую форму (документ 09), и проверка это пропустит.
- **Набор мал** (11 документов), и на настоящей модели он почти не нагружает защиту
  (см. «Честная оговорка» в разделе Eval).
- `field_confidence` — простые правила, а не откалиброванные вероятности.
- Нет обработки нескольких документов за раз, PDF и картинок: на вход идёт только текст.
- Сравнение в eval: названия позиций сравниваются мягко, а позиции — по порядку, без сопоставления.

**Что сделала бы дальше:** расширила бы набор до 50+ документов, включая «враждебные», где модель
действительно галлюцинирует; добавила бы проверку дат кодом по ключевым словам
(«от», «составлено», «действительно до»); сделала бы eval с несколькими прогонами модели,
чтобы видеть разброс; сравнила бы несколько моделей на одном наборе.
